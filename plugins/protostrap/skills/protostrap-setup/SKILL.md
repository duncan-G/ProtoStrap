# Setting up an application repository

An application uses ProtoStrap **at a version**, from GitHub (`duncan-G/protostrap`): its
Terraform modules, its reusable workflows, and the source those workflows build the
`protostrap` CLI and the edge image from. Nothing of ProtoStrap is copied into the
application. ProtoApp (an Aspire app) and ProtoStrap's `sample/` are worked examples.

Ground truth is ProtoStrap's `docs/production.md`, `infra/README.md` and `sample/README.md`
at the version you pin. Templates for every file are in
[references/templates.md](references/templates.md).

## The layout

```
protostrap.yaml                  the spec (protostrap-spec), or generated by the AppHost (protostrap-aspire)
src/ or services/                the code (protostrap-contract)
infra/
  bootstrap/<env>/main.tf        per account: Org Admin applies once, from their machine
  bootstrap/<env>/terraform.tfvars.example
  <env>/main.tf                  per account: the platform, applied by the infra workflow
.github/workflows/
  deploy.yml                     plan → infra if changed → deploy, per environment
  infra.yml                      plan, apply or destroy by hand; applies on root changes
  ci.yml                         tests, spec drift and check, terraform fmt and validate
scripts/set-secrets.sh           optional: the app's own keys, through ProtoStrap's set-secret.sh
```

One application per AWS account, one account per environment, all in the same region.

## The version, everywhere

Every reference names the same version. **Never point one at a branch, and never move a tag.**

| Where                               | Form                                                                  |
| ----------------------------------- | --------------------------------------------------------------------- |
| The spec                            | `protostrap: 0.1.0` (from `WithVersion("0.1.0")` with Aspire)         |
| Every reusable workflow call        | `uses: duncan-G/protostrap/.github/workflows/<name>.yml@v0.1.0` and `protostrap-ref: v0.1.0` |
| CI's ProtoStrap checkout            | `ref: v0.1.0`                                                         |
| Every Terraform root                | `source = "github.com/duncan-G/protostrap//infra/<module>?ref=v0.1.0"` |
| ProtoStrap.Hosting (Aspire only)    | A checkout at `v0.1.0`, or `PackageReference … Version="0.1.0"` once published |
| The Claude plugin, if pinned        | `.claude/settings.json`: the marketplace's `"ref": "v0.1.0"`          |

Find them all by the current version itself, then read each hit:

```bash
grep -rnF --exclude-dir={.git,.protostrap,.terraform,bin,obj,node_modules} '0.1.0' .
```

## Adding ProtoStrap to an application

1. **Write the spec** (protostrap-spec skill) or the AppHost (protostrap-aspire skill). `app`
   is short and lowercase: it names the secret, `<app>/<environment>`, and the log groups.
   Leave `hosts` out when they differ per account, and route by path.
2. **Make the code keep the contract** (protostrap-contract skill).
3. **Add the Terraform roots** for the first account, from the templates: a bootstrap root
   (`app`, `environment`, `github_repository`, the platform's `infra_variables`) and a platform
   root (`spec = file(".../protostrap.yaml")`, `environment`, hosts and Cloudflare inputs).
   Gitignore `terraform.tfvars`, `.terraform/` and `*.tfstate*`.
4. **Add the workflows** from the templates. Callers must grant
   `permissions: { contents: read, id-token: write }`: the reusable workflows sign in to AWS
   with GitHub's OIDC token. Pass `apphost:` to `plan.yml` when an AppHost writes the spec.
   **Never name the caller's `concurrency` group `deploy-<environment>`:** the reusable
   deploy job already holds that group, and GitHub cancels a run whose workflow and job
   groups collide. Use `deploy`, never cancelled.
5. **Check it offline:**

   ```bash
   terraform fmt -check -recursive infra
   ```

   ```bash
   terraform -chdir=infra/dev init -backend=false && terraform -chdir=infra/dev validate
   ```

   and `protostrap check` on the spec (protostrap-spec skill).
6. **Hand the account steps to an Org Admin.** You can't do these: they need the account's
   admin credentials, a Cloudflare token and secret values. Write them out in order:
   1. `terraform -chdir=infra/bootstrap/dev init` and `apply`, with `AWS_PROFILE` and
      `GITHUB_TOKEN=$(gh auth token)`. It creates the state bucket, OIDC provider, Infra and
      Deploy roles, and the `dev` and `dev-infra` GitHub environments with their variables.
      If the account already has GitHub's OIDC provider, set
      `create_github_oidc_provider = false` in the module.
   2. `gh secret set CLOUDFLARE_API_TOKEN --env dev-infra` (token permissions: ProtoStrap's
      `sample/README.md#what-you-need`).
   3. `gh workflow run infra.yml -f action=plan`, then `-f action=apply`.
   4. Secrets: the tunnel's token with ProtoStrap's script, with `CLOUDFLARE_ACCOUNT_ID`,
      `CLOUDFLARE_API_TOKEN`, `AWS_PROFILE` and `AWS_REGION` set:
      `../ProtoStrap/scripts/set-edge-token.sh <app> dev` (or `.protostrap/scripts/…`). Then
      every component's keys (protostrap-secrets skill), PostgreSQL's and Redis's passwords
      included.
   5. Push to `main`, or `gh workflow run deploy.yml`. The first deploy builds every image,
      so it is the slowest.

## Adding production

Production is its own account and its own pair of roots, `infra/bootstrap/prod` and
`infra/prod`. Follow ProtoStrap's `docs/production.md` in order; in the repository that means:

- **`infra/prod/main.tf`** like dev's, but keep `protect_data_vms` (true) and `force_destroy`
  (false) at their defaults, and set retentions (`log_retention_days = 90`,
  `backup_retention_days = 35`, `snapshot_retention = 14`) and `client_rate_limit`.
  `vpc_cidr` can't change later.
- **`deploy.yml`** gains `approve` (environment `prod-approval`, created by hand with required
  reviewers), then `prod-plan`, `prod-infra`, `prod` jobs: one approval per release. An
  `infra-prod.yml` like `infra.yml` runs prod's plan, apply or destroy by hand.
- **The Org Admin's steps** repeat for prod: bootstrap `infra/bootstrap/prod`,
  `gh secret set CLOUDFLARE_API_TOKEN --env prod-infra` (a token scoped to prod's zone),
  confirm the alert emails, then the edge token and every key in `<app>/prod`.
- **GitHub:** required reviewers on `prod-approval` and `prod-infra`; `prod` and `prod-infra`
  limited to `main`; a ruleset on `main` requiring review and `ci`; `CODEOWNERS` for
  `protostrap.yaml` and `infra/`.
- **The spec:** services that must stay up have `min: 2`; the data VM fits PostgreSQL and Redis
  with room; every `max` is chosen knowingly; images pinned. Optionally a spec per environment
  (`protostrap.dev.yaml`), passed as `spec:` to dev's jobs and read by dev's root.
- **Base images pinned by digest,** so prod builds what dev tested.
- **Dead-letter alarms** per queue in `infra/prod/main.tf`, an outside uptime check, and an
  AWS Budget: ProtoStrap creates none of them.

Before go-live, walk the checklist at the end of `docs/production.md#8-go-live` with the user.

## Upgrading ProtoStrap

1. **Read what changed** between the two tags: ProtoStrap's commits and `docs/` diff
   (`git -C ../ProtoStrap log --oneline v0.1.0..v0.2.0 -- docs infra .github hosting` or the
   compare view on GitHub). Look for new required inputs, renamed variables, and upgrade
   sections such as `docs/secrets.md#upgrading`.
2. **Change every reference in one pull request** (the table above), regenerate the spec if an
   AppHost writes it, and run `protostrap check` with the new version's CLI.
3. **Do the migration steps** the docs name, in their order. Some need an Org Admin before
   the deploy (a bootstrap apply, new secret keys); say so in the pull request.
4. **It deploys like any release:** dev first, then prod after approval. The scheduler updates
   first, then the agents on their next sync.

## Don't

- Point a workflow or module at `main`, or mix versions between files.
- Give pull-request workflows the Deploy role, or skip `prod-approval`.
- Run bootstrap, the infra apply, or `set-secret.sh` yourself; write the commands.
- Commit `terraform.tfvars`, state, or a Cloudflare token.
