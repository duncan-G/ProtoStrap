# Setting up an application repository

An application uses ProtoStrap **at a version**, from GitHub (`duncan-G/protostrap`): its
Terraform modules, its reusable workflows, and the source those workflows build the
`protostrap` CLI and the edge image from. Nothing of ProtoStrap is copied into the
application. ProtoApp (an Aspire app) and ProtoStrap's `sample/` are worked examples.

Ground truth is ProtoStrap's `docs/production.md`, `infra/README.md` and `sample/README.md`
at the version you pin. Templates for every file are in
[references/templates.md](references/templates.md).

## The layout

```
protostrap.yaml                  the spec (protostrap-spec), or generated by the AppHost (protostrap-aspire)
src/ or services/                the code (protostrap-contract)
infra/
  bootstrap/main.tf              the account's bootstrap: Org Admin applies once, from their machine
  bootstrap/terraform.tfvars.example
  prod/main.tf                   prod's platform, applied by the infra workflow
  people/main.tf                 who signs in where: Org Admin applies once, in the same account
  people/terraform.tfvars.example
.github/workflows/
  deploy.yml                     approve → plan → infra if changed → deploy, to prod
  infra.yml                      plan, apply or destroy by hand; applies on root changes
  ci.yml                         tests, spec drift and check, terraform fmt and validate
scripts/set-secrets.sh           optional: the app's own keys, through ProtoStrap's set-secret.sh
```

One AWS account per application, in one region. It holds everything: IAM Identity Center,
as its organization's management account, prod's platform, and dev's secret.
**Dev is the local run** (`aspire run`), never a deployed environment, and has no account:
its secret, `<app>/dev`, which Developers run services with, sits beside prod's,
`<app>/prod`. Dev has no bootstrap or platform root, workflow, GitHub environment, hostname
or spec. Prod is the deployed environment.

## The version, everywhere

Every reference names the same version. **Never point one at a branch, and never move a tag.**

| Where                               | Form                                                                  |
| ----------------------------------- | --------------------------------------------------------------------- |
| The spec                            | `protostrap: 0.1.1` (from `WithVersion("0.1.1")` with Aspire)         |
| Every reusable workflow call        | `uses: duncan-G/protostrap/.github/workflows/<name>.yml@v0.1.1` and `protostrap-ref: v0.1.1` |
| CI's ProtoStrap checkout            | `ref: v0.1.1`                                                         |
| Every Terraform root                | `source = "github.com/duncan-G/protostrap//infra/<module>?ref=v0.1.1"` |
| ProtoStrap.Hosting (Aspire only)    | A checkout at `v0.1.1`, or `PackageReference … Version="0.1.1"` once published |
| The Claude plugin, if pinned        | `.claude/settings.json`: the marketplace's `"ref": "v0.1.1"`          |

Find them all by the current version itself, then read each hit:

```bash
grep -rnF --exclude-dir={.git,.protostrap,.terraform,bin,obj,node_modules} '0.1.1' .
```

## Adding ProtoStrap to an application

1. **Write the spec** (protostrap-spec skill) or the AppHost (protostrap-aspire skill). `app`
   is short and lowercase: it names the secret, `<app>/<environment>`, and the log groups.
   Add `tunnel: {}`, `gateway` and `telemetry: {}` (with Aspire, `AddCloudflareTunnel`,
   `AddEnvoyGateway` and `AddTelemetry`) for what the application uses: each runs only when
   present, and an application served from the internet needs the first two.
   Name each host in `gateway.hosts`, and route by those names: each account's platform root
   gives every name its hostname there with `hosts`.
2. **Make the code keep the contract** (protostrap-contract skill).
3. **Add the Terraform roots** for prod, from the templates: a bootstrap root (`app`,
   `environment`, `github_repository`, the platform's `infra_variables`), a platform root
   (`spec = file(".../protostrap.yaml")`, `environment`, hosts and Cloudflare inputs), and the
   people root (`accounts`: prod's, the one account, which holds dev's secret too).
   Gitignore `terraform.tfvars`, `.terraform/` and `*.tfstate*`.
4. **Add the workflows** from the templates. Callers must grant
   `permissions: { contents: read, id-token: write }`: the reusable workflows sign in to AWS
   with GitHub's OIDC token. Pass `apphost:` to `plan.yml` when an AppHost writes the spec.
   **Never name the caller's `concurrency` group `deploy-<environment>`:** the reusable
   deploy job already holds that group, and GitHub cancels a run whose workflow and job
   groups collide. Use `deploy`, never cancelled.
5. **Check it offline:**

   ```bash
   terraform fmt -check -recursive infra
   ```

   ```bash
   terraform -chdir=infra/prod init -backend=false && terraform -chdir=infra/prod validate
   ```

   and `protostrap check` on the spec (protostrap-spec skill).
6. **Hand the account steps to an Org Admin.** You can't do these: they need the account's
   admin credentials, a Cloudflare token and secret values. Write them out in order:
   1. `terraform -chdir=infra/people init` and `apply`, with `AWS_PROFILE` for the account,
      its organization's management account, once Identity Center is enabled in its console.
      `accounts` is `{ prod = "<the account's ID>" }`: dev has none. Then people are added
      to `Org-Admins`, `Platform-Admins` and `Developers` in Identity Center.
   2. `terraform -chdir=infra/bootstrap init` and `apply`, with `AWS_PROFILE` and
      `GITHUB_TOKEN=$(gh auth token)`. It creates the state and deploy buckets, OIDC provider, Infra and
      Deploy roles, and the `prod` and `prod-infra` GitHub environments with their variables.
      If the account already has GitHub's OIDC provider, set
      `create_github_oidc_provider = false` in the module.
   3. `gh secret set CLOUDFLARE_API_TOKEN --env prod-infra` (a token scoped to prod's zone;
      its permissions: ProtoStrap's `sample/README.md#what-you-need`).
   4. In GitHub, before anything deploys: `prod-approval` created by hand with required
      reviewers, required reviewers on `prod-infra`, and all three environments limited to
      `main`.
   5. `gh workflow run infra.yml -f action=plan`, then `-f action=apply`. Then confirm the
      alert emails.
   6. Secrets: with a tunnel in the spec, its token with ProtoStrap's script, with
      `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, `AWS_PROFILE` and `AWS_REGION` set:
      `../ProtoStrap/scripts/set-edge-token.sh <app> prod` (or `.protostrap/scripts/…`). Then
      every key in `<app>/prod` (protostrap-secrets skill), PostgreSQL's and Redis's
      passwords included.
   7. Push to `main`, or `gh workflow run deploy.yml`, and a reviewer approves it in
      `prod-approval`. The first deploy builds every image, so it is the slowest.

## Before go-live

The first deploys go to prod while it serves no one yet: run the checks there. Follow
ProtoStrap's `docs/production.md` in order; in the repository that means:

- **`infra/prod/main.tf`** keeps `protect_data_vms` (true) and `force_destroy` (false) at
  their defaults, and sets retentions (`log_retention_days = 90`,
  `backup_retention_days = 35`, `snapshot_retention = 14`) and `client_rate_limit`.
  `vpc_cidr` can't change later.
- **GitHub:** required reviewers on `prod-approval` and `prod-infra`; `prod-approval`, `prod`
  and `prod-infra` limited to `main`; a ruleset on `main` requiring review and `ci`;
  `CODEOWNERS` for `protostrap.yaml` and `infra/`.
- **The spec:** services that must stay up have `min: 2`; the data VM fits PostgreSQL and Redis
  with room; every `max` is chosen knowingly; images pinned.
- **Base images pinned by digest** (protostrap-contract's "The image").
- **Dead-letter alarms** per queue in `infra/prod/main.tf`, an outside uptime check, and an
  AWS Budget: ProtoStrap creates none of them.

Before go-live, walk the checklist at the end of `docs/production.md#8-go-live` with the user.

## Another deployed environment

Only when the user asks for one, and never one called dev: dev is the local run. It is its
own account with its own pair of roots, a bootstrap root and `infra/<environment>`, copies
of `infra/bootstrap` and `infra/prod` with its `environment`, and:

- its account in the people root's `accounts`;
- its own plan, infra and deploy jobs in `deploy.yml`, and an `infra-<environment>.yml` like
  `infra.yml`;
- its own hostnames, and its own email domain if it sends mail (protostrap-email);
- the Org Admin's steps above, for it;
- optionally a spec of its own, `protostrap.<environment>.yaml`, passed as `spec:` to its
  jobs and read by its root (protostrap-spec's "One spec or two?").

## Upgrading ProtoStrap

1. **Read what changed** between the two tags: ProtoStrap's commits and `docs/` diff
   (`git -C ../ProtoStrap log --oneline v0.1.0..v0.2.0 -- docs infra .github hosting` or the
   compare view on GitHub). Look for new required inputs, renamed variables, and upgrade
   sections such as `docs/secrets.md#upgrading`.
2. **Change every reference in one pull request** (the table above), regenerate the spec if an
   AppHost writes it, and run `protostrap check` with the new version's CLI.
3. **Do the migration steps** the docs name, in their order. Some need an Org Admin before
   the deploy (a bootstrap apply, new secret keys); say so in the pull request.
4. **It deploys like any release:** to prod, after approval. The scheduler updates first,
   then the agents on their next sync.

## Don't

- Point a workflow or module at `main`, or mix versions between files.
- Deploy to dev, or give it an account: no `infra/bootstrap/dev`, `infra/dev`,
  `protostrap.dev.yaml` or dev jobs. Dev is the local run.
- Give pull-request workflows the Deploy role, or skip `prod-approval`.
- Run bootstrap, the infra apply, or `set-secret.sh` yourself; write the commands.
- Commit `terraform.tfvars`, state, or a Cloudflare token.
